# Скилл артефактов надстройки software-development-workflow

## Назначение и граница

Скилл — процедура для агента, а не исполняемый установщик: файлы создаёт и
правит агент своими инструментами, значимые решения согласуются с
пользователем. Он упаковывает обязанности надстройки — HLD, контракты
синхронных API и асинхронных событий, описание данных, технический долг и
конфигурацию подключения, — не дублируя upstream skills: SPEC, планы, задачи,
CONSTRAINTS, ADR и CHANGELOG ведутся применимыми upstream skills по их
собственным конвенциям.

Первоисточник требований — документы стандарта закреплённой ревизии. При
расхождении скилла и стандарта приоритет у стандарта.

## Материалы стандарта

Найдите корень снимка стандарта (далее `<стандарт>`):

1. В продуктовом репозитории: `.agents/references/software-development-workflow/`
   или `.claude/references/software-development-workflow/`.
2. В самом репозитории стандарта: корневые `docs/`, `templates/`, `examples/`
   и `upstream.lock.yaml`.

Ключевые документы: `<стандарт>/docs/artifacts.md` — каталог артефактов и
условия их создания; `<стандарт>/docs/metadata.md` — контракт frontmatter;
`<стандарт>/docs/integration.md` — профили и конфигурация;
`<стандарт>/docs/upstream.md` — этапы процесса и дополнения к навыкам;
`<стандарт>/docs/governance.md` — правила проверки. Шаблоны — в
`<стандарт>/templates/`, ориентир по объёму — `<стандарт>/examples/`.

Правила конкретного продукта возьмите из `.workflow/config.yaml`: профиль,
`capabilities`, `required_artifacts`, `paths`, `task_tracking`, `exceptions`.
Конфигурация — декларативное соглашение; её чтение и правка выполняются агентом
вручную по `<стандарт>/docs/integration.md`.

## Инициализация нового продукта

Вызывается платформенной настройкой (шаг инициализации репозитория в
`go-platform-bootstrap`) или запросом пользователя. Цель — конфигурация и
минимальный набор документов выбранного профиля, заполненные фактами о
продукте, без пустых файлов ради дерева каталогов.

1. Осмотр без изменений: README, `AGENTS.md` и `CLAUDE.md`, `docs/`,
   `MANUAL.md`, код. Определите существующие документы и их состояние.
   Существующее не перезаписывать и не переименовывать.
2. Согласуйте с пользователем профиль (`lean` / `standard` / `critical`),
   `capabilities` и `paths`, если платформенная настройка их ещё не
   зафиксировала.
3. Если `.workflow/config.yaml` отсутствует, создайте его из
   `<стандарт>/examples/workflow.yaml`, заполнив все `<...>`: revision
   стандарта, upstream из `<стандарт>/upstream.lock.yaml`, платформу или
   `null`, профиль, capabilities и фактические пути. Существующую конфигурацию
   сверяйте с контрактом интеграции и дополняйте пробелы, сохраняя принятые
   решения.
4. Создайте документы по таблице ниже; шаблоны — из `<стандарт>/templates/`,
   ориентир по объёму — `<стандарт>/examples/`. Каркас без содержания не
   создавайте: документ либо заполняется фактами, либо не создаётся.

| Артефакт | При инициализации | Позже |
| --- | --- | --- |
| `docs/hld/README.md` | да — краткий HLD | при изменении системной архитектуры |
| `docs/api/<boundary>.md` | нет | с первой реальной границей |
| `docs/events/<event>.md` | нет | с первым событием |
| `docs/data/README.md` | нет | с долговечными данными |
| `docs/debt/DEBT-NNNN.md` | нет | с первым подтверждённым долгом |

Список обязателен к расширению, если `capabilities` или `required_artifacts`
конфигурации включают соответствующие артефакты сразу.

5. Заполняйте документы только фактами из репозитория и ответов пользователя:
   контекст, компоненты, развёртывание и NFR — из кода, `MANUAL.md` и
   обсуждения. Неизвестное помечайте как пробел, не выдумывайте. Для HLD
   проставьте `reality`: `current`, `target` или `mixed` с явной пометкой
   целевых разделов.
6. Frontmatter — по контракту `<стандарт>/docs/metadata.md`: `schema_version`,
   уникальный `id` продукта, `type` из каталога, `language: ru`, реальный
   `owner`, даты в формате `YYYY-MM-DD`. Статус `active` — когда документ
   отражает проверенное состояние; при открытых пробелах оставьте `draft`.
7. Если платформенная настройка уже создала HLD из собственного шаблона —
   дополните его до требований каталога (раздел решений со списком ADR,
   эксплуатация и безопасность по применимости), не перезаписывая имеющиеся
   разделы и решения.
8. Отчёт: созданные и изменённые файлы, открытые пробелы, что требуется
   согласовать. Изменения фиксируются обычным коммитом продукта.

## Подключение существующего продукта

Начните с инвентаризации без изменений: реальные пути, ID, статусы, машинные
контракты, трекер — по `<стандарт>/docs/governance.md`. Составьте карту
документов, добавьте frontmatter без переписывания принятых решений; перенос
выполняйте порциями с проверкой обратных ссылок и команд адаптеров. Дату
неизвестного создания определите по истории Git или пометьте пробелом до
миграции; не выдумывайте.

## Ведение при разработке

Артефакты надстройки меняются вместе с кодом; влияние фиксируется в разделе
проверки существующего плана или задачи upstream — отдельные документы для
этого не создаются.

| Событие | Действие |
| --- | --- |
| Изменение внешнего или межмодульного интерфейса | обновить затронутый `docs/api/<boundary>.md`; машинный первоисточник первичен, Markdown не дублирует его целиком |
| Появление или изменение события | обновить `docs/events/<event>.md` |
| Изменение модели долговечных данных | обновить раздел домена в `docs/data/README.md` |
| Подтверждённый технический долг | создать `docs/debt/DEBT-NNNN.md`; гипотеза сначала проверяется |
| Значимое архитектурное решение | ADR по upstream-конвенции `documentation-and-adrs`, затем запись в списке решений HLD |
| Изменение системной архитектуры или эксплуатации | обновить соответствующие разделы HLD |
| Смена профиля, `paths` или `capabilities` | отдельное изменение конфигурации с оценкой недостающих документов |

Порядок: до изменения прочитать затронутые HLD и контракты и зафиксировать
влияние; после — обновить фактическое состояние и приложить результаты
проверок. Если влияние отсутствует, кратко объясните почему. Ссылки на задачи
ведутся через `external_refs` без дублирования статусов трекера.

## Проверка

Структурная — по `<стандарт>/docs/governance.md`: поля и допустимые значения
frontmatter, глобальная уникальность ID, разрешение `related`, относительные
ссылки, отсутствие шаблонных подсказок в готовых документах, обязательные
артефакты выбранного профиля и `capabilities`, актуальность исключений.
Содержательная: HLD — с кодом; контракты — с машинными первоисточниками; долг —
с признаками в коде; список ADR в HLD — с фактическим каталогом решений
продукта. Недостаток данных — результат «не подтверждено», а не положительный
вывод.

## Правила

- Текст документов — на русском; frontmatter, ключи YAML, код и
  API-идентификаторы — без перевода.
- Не создавайте пустые документы ради структуры каталога.
- Не ведите в этом скилле артефакты upstream: SPEC, планы, задачи, CONSTRAINTS,
  ADR, CHANGELOG.
- Не перезаписывайте существующие пользовательские документы и историю
  принятых решений.
- Все изменения — в Git продукта; конфигурация сама ничего не запускает.
