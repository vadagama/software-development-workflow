# Интеграция, профили и настройка

Платформенный репозиторий ссылается на конкретный commit этого стандарта, определяет допустимые компоненты, собственную структуру исходников, команды сборки/тестов/проверок и дополнительные ограничения. Стандарт не выбирает Go, PostgreSQL, облако, фреймворк или трекер за платформу.

Продукт хранит `.workflow/config.yaml` по [примеру](../examples/workflow.yaml). Конфигурация и документы должны входить в Git; их нельзя помещать только в игнорируемый служебный каталог платформы. Один URL в README не заменяет доступность файлов для агента: нужная версия стандарта и upstream должна быть доступна локально либо через чтение закреплённых URL.

## Поля конфигурации

| Поле | Контракт |
| --- | --- |
| `config_version` | Формат конфигурации, сейчас `1` |
| `standard` | `repository`, `revision` — полный commit SHA; `version` — редакция |
| `upstream` | `repository`, `revision` из lock; фактически доступная версия должна совпасть |
| `platform` | `null` для независимого продукта либо repository + revision + путь правил |
| `profile` | `lean`, `standard`, `critical` |
| `documentation` | `language: ru`, `format: markdown-frontmatter`, `schema_version: 1` |
| `capabilities` | Список из `api`, `data`, `events`, `ui`, `operations`, `sensitive-data`; влияет на применимость |
| `required_artifacts` | Дополнительные типы из каталога; дополняют профиль |
| `task_tracking` | `mode: local` и путь либо `mode: external`, provider, project URL и mapping |
| `paths` | Пути HLD, API, событий, данных и долга от корня продукта |
| `exceptions` | Список документированных исключений по правилам профилей |

Конфигурация — декларативное соглашение, автоматического resolver пока нет. Неизвестные поля или значения нужно разобрать как ошибку настройки, а не молча игнорировать. При внешнем трекере `todo` не создаётся; `mapping` описывает представление русских Markdown-описаний и frontmatter.

## Профили

Профиль управляет глубиной документации и условиями подключения практик, но не снижает проверки применимого upstream skill. Не создавайте пустые документы ради дерева каталогов.

| Профиль | Минимум | По условиям |
| --- | --- | --- |
| `lean` | README, AGENTS, конфигурация, краткий HLD | Контракты при наличии границы или событий; `docs/data` при долговечных данных |
| `standard` | Минимум `lean`; долг при подтверждённых технических проблемах | SPEC/план для значимой работы — по конвенциям upstream |
| `critical` | Минимум `standard`; измеримые NFR, анализ угроз в HLD | Для эксплуатируемой системы — SLO, восстановление и откат в HLD |

`standard` — рекомендуемый исходный профиль. `critical` выбирается по последствиям отказа, а не по размеру команды. Исследовательский прототип использует `lean`; перед превращением в продукт его профиль и пробелы пересматриваются.

Независимо от профиля действуют язык, frontmatter, уникальные ID и проверка актуальности. Для любого профиля наличие API, данных и событий включает соответствующие контракты; чувствительная информация и эксплуатация требуют соответствующих разделов HLD. Упрощение означает меньший объём, а не пропуск важного содержания.

Списки добавочных требований (`capabilities`, `required_artifacts`, `paths`, `exceptions`) объединяются без дубликатов; удаление требования через пустой список не допускается. Скалярные настройки продукта уточняют платформенный default в разрешённых пределах. Каждое исключение содержит правило, основание, область, владельца, доказательство согласования, компенсирующую меру и дату пересмотра. Конфликт обязательных требований нельзя разрешать принципом «последний файл победил». Неизменяемые требования этого стандарта (русский язык, Markdown + frontmatter) не отменяются профилем; их изменение требует новой версии стандарта.

Смена профиля — отдельное изменение конфигурации с оценкой недостающих документов. Понижение профиля не удаляет историю, открытый долг и обязательства платформы. Нельзя менять профиль только ради прохождения текущей проверки.

## Порядок применения

1. Прочитать закреплённые версии и проверить доступность skills. Глобальная установка не гарантирует изоляцию версий между продуктами.
2. Применить upstream как базовый процесс и этот стандарт как соглашения о документации. Явно сопоставить альтернативные пути из `paths` с потребителями. Инициализацию конфигурации и минимальных документов ведёт агент по скиллу `software-development-workflow-addons` из снимка стандарта.
3. Применить требования платформы в её области ответственности; например, команды тестов берутся оттуда, а не из примеров TypeScript в upstream.
4. Выбрать профиль и дополнительные условия продукта. Настройки продукта могут усиливать обязательные требования; ослабления требуют предусмотренного исключения.
5. При несовместимых требованиях зафиксировать конфликт и разрешить его с владельцами правил до зависимой работы. Не менять upstream или стек незаметно.

В `AGENTS.md` продукта задаются язык, форматы, пути, источник задач и ссылки на стандарт, платформу и конфигурацию. [Фрагмент подключения](../examples/product-agents.md) адаптируется к фактическим путям. `CLAUDE.md` и иные файлы хостов при необходимости ссылаются на эти же соглашения, не создавая вторую копию политики.

## Совместимость с upstream

SPEC, планы, задачи, CONSTRAINTS, ADR и CHANGELOG ведутся upstream skills в их конвенциях: `spec-driven-development` для спецификаций, `planning-and-task-breakdown` для планов и задач, `documentation-and-adrs` для значимых решений. Поле `paths` закрепляет только артефакты надстройки — HLD, контракты API и событий, описание данных и долг. Upstream skills принимают соглашения проекта о формате и путях, поэтому переназначение не требует правки skills.

Slash-команды, hooks и адаптеры хостов могут содержать жёсткие пути. Их совместимость с frontmatter и альтернативными путями необходимо проверить до объявления интеграции готовой. Эта редакция не заявляет, что протестировала все хосты и платформы.
