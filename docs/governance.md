# Развитие и проверка стандарта

## Версии и их смена

Разделяйте четыре версии: редакция стандарта, версия формата метаданных (`schema_version`), upstream SHA и платформа SHA. Продукт обновляет их явно через review; смена `main` в удалённом репозитории не изменяет правила уже подключённого продукта.

Версии стандарта используют SemVer: patch — уточнения без новых обязанностей; minor — совместимые необязательные возможности; major — обязательные поля, удаление полей, изменение путей по умолчанию или поведения gates. До `1.0.0` несовместимое изменение увеличивает minor и всё равно требует миграционного описания. Изменение формата отдельно увеличивает `schema_version` или `config_version`.

## Изменение правил

1. Описать проблему, затронутые профили, совместимость и критерии результата.
2. Проверить, решается ли она настройкой существующего upstream skill. Предпочесть соглашение проекта новому skill, а новый узкий skill — переписыванию upstream.
3. Для значимого изменения записать ADR этого стандарта; изменить правила, шаблоны и примеры вместе.
4. Проверить сценарии из раздела «Сценарии приёмки» ниже, включая прежние продукты.
5. Добавить CHANGELOG и инструкцию перехода: старое → новое, порядок, ручные действия, проверка, rollback.
6. Опубликовать версию обычным процессом review и выпуска. Создание файлов само по себе не означает выпуск тега.

## Обновление upstream

Сравнить текущий SHA из `upstream.lock.yaml` с кандидатом, прочитать изменения использованных skills и host adapters, проверить [границу переиспользования](upstream.md) и сценарии. Только после этого изменить lock. Не подменять pinned SHA ссылкой на `main`. Если понадобится patch, хранить его отдельно с причиной, исходным SHA и условиями удаления; не включать одновременно оригинальный и изменённый skill одинакового назначения. В текущей редакции patches отсутствуют.

## Подключение существующего продукта

Сначала инвентаризация: реальные пути, ID, статусы, активные планы, трекер, машинные контракты. Сохранить существующие ID. Добавить frontmatter без переписывания принятых решений; дату неизвестного создания определить по истории или отметить пробел до миграции, не выдумывать. Составить карту путей и ссылок. Переносить порциями, проверяя обратные ссылки и команды адаптеров. Новый формат метаданных принять только после проверки документов; незавершённые планы не заменять.

Rollback возвращает конфигурацию и документы к совместимому коммиту через revert миграционного изменения; не удаляет новые продуктовые решения. Если новые артефакты уже появились, сначала проверить их совместимость со старым форматом метаданных. Upstream, стандарт и платформа не обязаны обновляться одновременно.

## Проверка стандартов и продуктов

Проверка состоит из структуры и смысла. Структурная проверка полей не доказывает соответствие архитектуры коду. Ни YAML-конфигурация, ни этот документ автоматически не запускают проверки.

### Структурная проверка

- Безопасно разобрать frontmatter каждого авторского `.md`, отклоняя повторяющиеся ключи; проверить поля и допустимые значения по [контракту метаданных](metadata.md), включая формат дат `YYYY-MM-DD`.
- Проверить глобальную уникальность ID и разрешение каждого `related`; внешний URL хранить в `external_refs`.
- Проверить относительные ссылки, существование первоисточников и отсутствие шаблонных заполнителей в готовых документах.
- Проверить переходы статусов по Git diff, `created <= updated` и сохранение принятых решений.
- Проверить обязательные артефакты выбранного профиля и capabilities, актуальность исключений.
- Сверить закреплённые SHA с реально доступными версиями. Запустить команды платформы для контрактов, тестов и миграций.

Структурная проверка охватывает только поля и допустимые значения; ссылки, ID между файлами, смысл, переходы статусов, применимость профиля и корректность русской прозы требуют отдельных проверок. Пока автоматический валидатор не реализован, результаты записываются вручную в разделе проверки плана или задачи. Нельзя сообщать о пройденном CI, если он не запускался.

### Содержательная проверка

Сопоставить HLD с кодом; контракты API, событий и данные — с машинными первоисточниками; долг — с признаками в коде. Список ADR в HLD сверить с фактическим каталогом решений продукта. Каждое найденное расхождение должно иметь конкретные файлы и объяснение. Даты изменения Git дают сигнал для проверки, но сами не доказывают актуальность. При недостатке данных результат — «не подтверждено».

## Сценарии приёмки изменений стандарта

| Сценарий | Ожидаемый результат |
| --- | --- |
| Новый небольшой CLI, профиль lean | Краткий HLD и минимум правил; нет пустых API/Event документов |
| Продукт с API и БД | `docs/api` и `docs/data` ссылаются на машинный первоисточник, стек берётся из платформы |
| Событийная интеграция | События в `docs/events` с ссылками на producers/consumers и первоисточник |
| Подтверждённый долг | Запись `docs/debt/DEBT-NNNN.md` с доказательствами и владельцем; нет дублей ID |
| Изменение системной архитектуры | Обновляется HLD со связанным списком ADR, reality отражает переход; SPEC ведёт upstream |
| Смена профиля или upstream SHA | Есть оценка влияния и миграция; несовместимость не скрыта |
| Неизвестное состояние кода | Документ не объявлен актуальным без доказательств |
| Продукт на другом стеке | Нет навязанного Go/PostgreSQL; команды задаёт платформа |
| Ошибка метаданных или ссылок | Проверка отклоняет дубль ID, неверный статус и отсутствующий related |

Эти сценарии — требования к проверке и будущим evals, а не утверждение об уже выполненных интеграционных тестах.
