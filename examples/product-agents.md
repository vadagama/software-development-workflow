# Правила агента продукта — фрагмент подключения

Этот файл — пример для адаптации в `AGENTS.md` продукта. Перед использованием назначьте реальные ID, владельца и даты; добавьте ссылки на фактические правила платформы. Метаданные этого примера не переносятся без изменений.

1. Прочитай `.workflow/config.yaml`. Получи закреплённые версии стандарта, платформы и `addyosmani/agent-skills`; проверь совпадение версий с доступными файлами.
2. Следуй оригинальным применимым skills; процесс и карту расширений прочитай в `docs/upstream.md` **репозитория стандарта выбранной версии**.
3. Документация продукта — русский Markdown с YAML frontmatter по `docs/metadata.md` стандарта. Не переводить код, ключи YAML и API-идентификаторы.
4. Используй выбранные пути из конфигурации. По умолчанию HLD — `docs/hld/README.md`, контракты API — `docs/api`, события — `docs/events`, данные — `docs/data/README.md`, долг — `docs/debt`. Спецификации, планы и задачи ведутся по конвенциям upstream skills. Инициализацию и ведение этих документов ведёт скилл `software-development-workflow-addons` из набора навыков продукта.
5. Перед изменением прочитай затронутые HLD и контракты. Зафиксируй влияние; после реализации обнови их по фактическим изменениям и приложи результаты проверок в разделе проверки плана или задачи.
6. Технические компоненты, структуру кода и команды проверки бери из закреплённой платформы и правил продукта. Этот стандарт не задаёт стек.
7. При внешнем трекере создавай задачи только в нём, а в плане сохраняй ссылки. Не заводи параллельный список статусов. Незавершённые планы другой работы не перезаписывай.
8. Не объявляй target-архитектуру реализованной без доказательства. Значимые решения фиксируй по конвенции upstream `documentation-and-adrs`; историю не удаляй.
9. Не меняй профиль, pinned версии и исключения ради обхода неудачной проверки. Опиши конфликт и получи решение владельца соответствующего правила.
